# Spec: card-name autofill

Suggest card names as you type, in every search box, in **both v1 and v2**.

Cross-version on purpose, so this does not live under `docs/v2/`. The matching
and the data are shared code; only the four input components differ.

---

## Purpose

"I know it's a Charizard, I just can't spell Vikavolt."

Today every search box is a blank field that punishes a typo with a round trip
and an empty result. The catalog is the only thing that knows what a card is
called, and it is the slowest, least reliable thing in the app. Autofill moves
that knowledge onto the device, where it costs nothing to ask.

It also answers a question the current search cannot: **which Charizard.** There
are thirteen distinct card names beginning with "Charizard" — `Charizard`,
`Charizard ex`, `Charizard V`, `Charizard VMAX`, `Charizard VSTAR`,
`Charizard-GX`, `Charizard-EX`, `Charizard G`, `Charizard G LV.X`,
`Charizard δ`, `Charizard ★ δ`, `Charizard & Braixen-GX`,
`Charizard Spirit Link` — and no way to discover that before searching.

---

## The rule this must not break

> **Typing does not search. Submit does.**
> `docs/v2/specs/09-search-details.md`

pokemontcg.io fails roughly a quarter of the time in bursts and rate-limits.
A request per keystroke spends that budget on prefixes nobody asked about, and
it is the reason there is no debounced auto-search anywhere in this app.

**Autofill must therefore be answered entirely on the device.** No suggestion
endpoint, no per-keystroke fetch, no "search-as-you-type" that is really search.
Selecting a suggestion fills the box; it does not submit. Submit stays the only
thing that searches.

That constraint is what makes the feature affordable at all — see Data.

---

## Data

**A new build-time artefact: `public/card-index/names-<version>.json`.**

Generated by `scripts/build-card-index.mjs`, from the same source and in the
same run as the existing index, so the two cannot drift.

Measured against the current index (`cards-6defdc2b.json`, 20,205 cards):

|                       |           |
| --------------------- | --------- |
| Distinct card names   | **4,451** |
| Raw JSON              | **67 KB** |
| Gzipped over the wire | **21 KB** |

**Do NOT read `cards-<version>.json` for this.** It is **2.29 MB** — the full
per-card metadata, and it exists for the scanner, which needs a row per
printing. Pulling 2.3 MB onto a phone to help someone spell "Gyarados" is the
obvious implementation and the wrong one. The names file is 1% of it.

Shape — an array, so it stays small and ordered:

```json
[["Pikachu", 99], ["Eevee", 65], ["Raichu", 45], ...]
```

The second number is **how many printings carry that name**, and it is not
decoration: it is the ranking signal. See Ranking.

Loaded **lazily, once, on first focus of any search box**, and cached for the
session alongside the existing `loadCardIndex` pending-promise pattern. Never
loaded on Home, never on a screen with no search box, never eagerly.

---

## Ranking

The hard part. "char" must put `Charizard` first, not `Charcadet` or
`Charizard & Braixen-GX`, and a naive alphabetical sort gets this wrong every
time.

Order by, in sequence:

1. **Exact match** on the folded name.
2. **Prefix match** before **word-prefix match** before **substring match** —
   "char" prefixes `Charizard`; "brai" is a word-prefix of
   `Charizard & Braixen-GX`; "izar" is only a substring.
3. Within a tier, **more printings first**. Pikachu has 99 and some Trainer has
   one; the collector typing "pik" means the former. This is the whole reason
   the count ships with the name.
4. Ties break alphabetically, so the order is stable and testable.

**Cap at 8 suggestions.** A list longer than a glance is a list you scroll
instead of read, and on a phone it covers the thing you were typing into.

---

## Matching

Fold before comparing, on both sides:

- **Case.** Obviously.
- **Diacritics and symbols.** `Charizard δ` and `Charizard ★ δ` are real names
  in this catalog. Someone typing "charizard d" should not be punished, and
  someone typing "δ" should still match. Fold to a comparable form, and keep
  the ORIGINAL for display — the suggestion must show the card's real name,
  because that is what they will see on the results screen.
- **Punctuation and spacing.** `Charizard-EX` and `Charizard ex` differ only in
  a hyphen, and `Charizard & Braixen-GX` carries an ampersand. Typing
  "charizard ex" must find `Charizard-EX`.

**Never rewrite what the user typed.** Autofill offers; it does not correct.
An inline "ghost completion" that silently changes the query on submit is how a
search box starts lying about what it searched for.

## Surfaces

Four input components, one shared hook. Each keeps its own submit behaviour.

| Version | Surface            | File                                     |
| ------- | ------------------ | ---------------------------------------- |
| v1      | App-bar search     | `src/web/shell/WebHeader.tsx`            |
| v1      | Binder card picker | `src/web/binders/WebBinderScreen.tsx`    |
| v2      | Search screen      | `src/v2/screens/search/SearchScreen.tsx` |
| v2      | Binder card picker | `src/v2/screens/binder/BinderPicker.tsx` |

**Out of scope, and worth saying why:**

- `src/v2/screens/collection/SetsView.tsx` and
  `src/v2/screens/scan/PickBySet.tsx` filter a list that is **already on
  screen**. Suggesting names there would offer cards that are not in the list
  being filtered.
- **The glasses.** `LetterPickerModal` is a four-gesture letter wheel on a
  600x600 additive display. A dropdown under a text field is not an
  interaction that shell has. Unchanged, deliberately.

## Accessibility

This is a **combobox**, and the ARIA pattern is not optional — it is the
difference between a feature and a trap for anyone not using a mouse.

- Input: `role="combobox"`, `aria-expanded`, `aria-controls`,
  `aria-autocomplete="list"`, and `aria-activedescendant` pointing at the
  highlighted option.
- List: `role="listbox"`; each suggestion `role="option"` with `aria-selected`.
- **Down/Up** move through suggestions; **Enter** takes the highlighted one, or
  submits the typed text when nothing is highlighted; **Escape** closes the list
  and leaves the text alone; **Tab** closes and moves on.
- A live region announces the count ("8 suggestions") when the list changes.
- Suggestions are ≥44px targets — `--v2-tap` in v2.

Note for v2: the wearable keyboard adapter is off there
(`createInputAdapter({ wearable: false })`), so Down/Up/Escape arrive
uninterrupted. In **v1** that adapter is live and `preventDefault`s exactly
these keys the moment anything subscribes — v1's implementation must confirm no
subscriber is active on the screen it is added to, or the arrow keys will be
eaten. This is the single most likely way the v1 half breaks.

## States

| State                   | What shows                                                                                                                        |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| Never focused           | Nothing. The file is not fetched.                                                                                                 |
| Focused, names loading  | Nothing — no spinner. It is 21 KB; a spinner would flash.                                                                         |
| Fewer than 2 characters | Nothing. One letter is 300 matches.                                                                                               |
| Matches                 | Up to 8, best first                                                                                                               |
| No matches              | The list closes. **No "no results" popup** — they may be typing a set name or a card this index predates, and submit still works. |
| Names file failed       | The box behaves exactly as it does today. Autofill is an enhancement and its absence must be invisible.                           |
| Offline                 | Suggestions still work once cached; that is the point of local data.                                                              |

## Acceptance

- [ ] Typing any number of characters issues **zero** network requests beyond
      the one-time names fetch. Asserted by counting requests, not by reading.
- [ ] The names file is not requested on a screen with no search box.
- [ ] "char" ranks `Charizard` above `Charcadet` and above
      `Charizard & Braixen-GX`.
- [ ] "pik" ranks `Pikachu` first — the 99-printing name, not the alphabetical
      one.
- [ ] "charizard ex" matches `Charizard-EX`.
- [ ] Selecting a suggestion fills the field and **does not search**; submitting
      after it searches once.
- [ ] Escape closes the list and leaves the typed text unchanged.
- [ ] Down/Up/Enter work in **v1** as well as v2 — i.e. the wearable adapter is
      not eating them.
- [ ] With the names file 404ing, every search box still submits normally.
- [ ] At 390px the list does not cover the input it belongs to.
- [ ] `getByRole("combobox")` and `getByRole("option")` find the control and its
      suggestions.

## Plan

Four steps. Each is independently shippable and leaves the app working.

### 1. The data — `scripts/build-card-index.mjs`

Emit `names-<version>.json` beside the existing files, same content hash, listed
in `latest.json`. Nothing consumes it yet.

_Done when:_ the file exists, is ~67 KB, and `latest.json` names it.

### 2. The shared logic — `src/models/cardNames.ts` + `src/services/`

Pure and tested, with no React and no DOM:

- `foldName(raw): string` — the comparison form.
- `rankNames(query, names, limit): Suggestion[]` — the ranking above.
- A loader beside `loadCardIndex`, sharing its lazy-once pattern.

This is the "kept column" (`docs/v2/PLAN.md` §1): shared by both versions, so it
is fixed in place rather than forked.

_Done when:_ unit tests cover every Ranking and Matching bullet, including the
thirteen Charizards and the Pikachu-vs-alphabetical case.

### 3. The v2 half — `src/v2/primitives/`

**Add the missing text-input primitive.** The handoff already records that
search and the binder picker each styled their own field, and that is exactly
the duplication that will double if autofill is bolted onto both separately.
One `SearchField` primitive with the combobox behaviour, a workshop entry
showing every state, then adopted by both v2 surfaces.

_Done when:_ `#/dev/workshop` shows it, both v2 boxes use it, and the v2 half of
Acceptance passes.

### 4. The v1 half — `WebHeader.tsx`, `WebBinderScreen.tsx`

Same hook, v1's own markup and CSS modules. v1 is not being restyled.

**Check the input adapter first.** See Accessibility.

_Done when:_ the v1 half of Acceptance passes, including arrow keys, and v1's
existing e2e is untouched and green.

### Order and risk

2 → 3 → 4, with 1 alongside 2. The riskiest step is **4**, because of the
adapter; the most valuable is **2**, because it is where every acceptance
criterion above is actually decided.

---

## Out of scope

- Fuzzy/typo-tolerant matching ("charzard"). Prefix and substring first; measure
  whether anyone needs more before paying for a trigram index.
- Suggesting set names, or cards you own. Different questions, different lists.
- Search history as suggestions — recent searches already exist on the v2 search
  screen's idle state and are a separate list with a different meaning.
- Anything under `src/scan/`. The names file is generated beside the scanner's
  index; the recogniser itself is untouched, and it is mirrored in
  `cardrec/judge.py` outside this repo.
